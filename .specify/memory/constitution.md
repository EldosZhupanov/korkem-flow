# KORKEM: правила применения Spec Kit

Версия адаптера: 1.0.0. Принят: 2026-09-09. Изменён: 2026-09-09.

## Источники решений

Это адаптер процесса, а не новая продуктовая конституция. Главные документы:
[PROJECT.md](../../PROJECT.md), [PLAN.md](../../PLAN.md),
[ROADMAP.md](../../ROADMAP.md), [NOW.md](../../NOW.md),
[CLAUDE.md](../../CLAUDE.md). Пути в этой секции — от .specify/memory/.

PROJECT задаёт назначение, PLAN — действующую архитектуру и R1–R10,
ROADMAP — порядок, NOW — текущую работу, CLAUDE — инженерные соглашения.
При конфликте раннего общего лозунга с явным последующим решением действует
это решение (например, PLAN R7 требует детерминированного пути до AI).
Спецификация описывает согласованное намерение; код и свежие тесты доказывают
фактическое состояние. Расхождение записывается, а не устраняется ослаблением
требования. Неразрешённое продуктовое противоречие блокирует только зависимую
работу и выносится владельцу.

Документы specs/ уточняют одну задачу со ссылкой на ROADMAP и NOW, не меняют
приоритеты, архитектуру, роли, модель размещения данных или цены самостоятельно.
Обновление этого адаптера не меняет R1–R10. Изменение правила сначала принимается
в основном документе и при необходимости ADR; затем обновляются ссылки здесь.

## Проверка R1–R10

Точный текст правил — [PLAN §2](../../PLAN.md#2-десять-инвариантов).
В plan.md каждой задачи заполнить все строки: применимость, конкретное
доказательство или обоснование N/A. Пустая клетка — незаконченный план.

| Правило | Что требуется проверить в затронутом пути |
|---|---|
| R1 | Бизнес-логика в domain; зависимости domain → AI отсутствуют |
| R2 | Мутация проходит существующий доменный сервис |
| R3 | UI/API/AI используют один путь действия |
| R4 | Компания определяется сессией; чужой объект отвергается |
| R5 | Отказ при попытке самостоятельно повысить роль |
| R6 | Производственные данные хранятся у клиента; внешние передачи соответствуют принятому решению |
| R7 | Реальное действие проходит при недоступном LLM |
| R8 | Отказ сети объясняется пользователю; доступная локальная работа сохраняется |
| R9 | Проверяются серверные права и фактическая запись аудита |
| R10 | AI-запись требует подтверждения и повторной валидации |

## Процесс

Для существенной задачи: spec → уточнения → plan → tasks → analyze →
implement → проверка требований. Малые исправления остаются в обычном процессе.
Не создавать новую архитектуру или миграции ради заполнения шаблона.
Перед кодом — проектный skill по области; перед bench — korkem-bench.

Каждое FR связывается с задачей и проверкой наблюдаемого результата.
Тесты прав, scope, денег, склада, транзакций и идемпотентности обязательны
там, где меняется соответствующее поведение. Интеграционный тест не подменяет
сам проверяемый сервис, права, базу и аудит. Моки внешнего провайдера допустимы.

Backend запускается исключительно через
infra/frappe_bench/scripts/run_tests.sh; один bench — одна операция.
Не менять состояние стенда во время чужого прогона. Не писать CI GREEN без
успешного remote run. Фиксировать команду, exit code, total, failures/errors,
skips и duration; пустой/пропущенный набор не доказывает требование.

Предыдущие diff сохраняются. Spec Kit сам не коммитит, не пушит и не меняет
ветку; Git extension, taskstoissues и внешние публикации требуют явного запроса.
При уже разрешённом полном цикле окончания отдельных команд не требуют
нового подтверждения перехода. Работать одним агентом, без автоматической
делегации из шаблонов.

## Оценка процесса

До кода зафиксировать исходные пробелы; во время работы — новые пропуски,
этап обнаружения, исправления после реализации и дополнительную документацию.
После проверки — фактический результат в evaluation.md и ссылки из NOW/ROADMAP.
Один пилот показывает конкретные находки, но не доказывает экономию времени
или снижение дефектов в процентах без сопоставимой исходной выборки.
