включая ранее начатые чужие изменения; это не clean checkout и не remote CI.

## Что применено

Официальный Spec Kit v1.0.4, pinned commit в
[upstream.json](../../.specify/upstream.json). Штатные интеграции Codex и Claude,
адаптер R1–R10 и четыре template overrides. Основные документы не заменены.

Штатные helpers создали feature и проверили prerequisites/выбор шаблонов;
spec → plan → tasks → сверка требований → код → проверка выполнены агентом.
Это не отчёт о запуске slash-команд в отдельной сессии Claude или Codex.

## Что пришлось переделать

До реализации план явно потребовал настоящий audit, retry, scope, rollback и
запрет commit. Это полезный проверочный список, но без контрольной задачи нельзя
утверждать, что эти требования обязательно были бы пропущены без Spec Kit.

После первой реализации исправлены **четыре неверных предположения тестов**:

1. Копия заказа переносила старую дату payment schedule — очищена для пересчёта.
2. Имя demo viewer не означает отсутствие производственной роли — создан свой
   пользователь с явно заданной ролью без доступа к этим действиям.
3. BOM выбранного заказа расходует не предположенный материал — остатки
   проверяются по настоящим строкам материального перевода.
4. Успешная отгрузка возвращает `delivered`, не `created` — сохранён текущий API-контракт.

Отдельно широкий AST выявил две старые инверсии domain → AI в invitations и
provisioning. Уточнена граница AST-gate пяти действий; долг не исправлен и не
выдаётся за закрытый. Подробности: [research.md](research.md).

При проверке установки выявлено ещё одно исправление процесса:
generic + codex дали `unsafe-multi-install`. Generic удалён штатным uninstall
(только 10 новых сгенерированных файлов), поставлен штатный Claude. Проверка
двух интеграций теперь OK, modified/missing managed files = 0.

Итог: Spec Kit **не устранил повторную работу**. Есть четыре исправления тестовых
предположений, одно уточнение границы и одно исправление установки. Изменений
бизнес-логики для прохождения пилота не потребовалось.

Первые диагностические прогоны были красными: 14 тестов / 11.559 s /

Это ошибки подготовки тестов и слишком широкого AST, не доказанные дефекты
пяти бизнес-действий. Их результаты не смешиваются с финальными зелёными.

Статическая проверка: `specify integration status` — OK; четыре результата
resolve-template совпадают с overrides побайтно; `bash -n` для шести helpers,
JSON parse метаданных и check-prerequisites с явным FEATURE_DIRECTORY — exit 0.
Контрольная подмена сервиса в одном специальном тесте вызывает llm.resolve и
получает AINotConfigured без изменения ERP. Это проверка ловушки, не отдельная
mutation-testing система. В пяти acceptance-сценариях сервисы не подменяются.

## Ограничения и решение

- Проверены API-функции + ERPNext, не новый HTTP/device E2E.
- Приложение korkem_ai установлено, но AI Settings.enabled=0 и вызовы текущих
  точек выбора провайдера запрещены. Удаление AI-приложения и любой произвольный
  будущий сетевой клиент этим тестом не покрываются.
- Demo baseline создаётся seed один раз до тестовых транзакций; каждый сценарий
  имеет свой rollback и запрет commit. Это не тест восстановления чистого стенда.
- Flutter не менялся этим пилотом и повторно здесь не запускался. Предыдущие
  результаты Flutter не выдаются за результаты новой проверки.
- Remote CI не запускался. Коммитов и push нет; прежний diff сохранён.

Затраты процесса: семь документов feature (включая этот), один guide, один
адаптер, четыре overrides и установка штатного scaffold. Хронометраж разработки
и сопоставимый baseline отсутствуют; длительность тестов выше — не срок разработки.

**Решение:** оставить Spec Kit как ограниченный пилот для существенных задач,
не вводить обязательные семь документов для мелких правок. Прослеживаемость
получилась явной, ERP-доказательств стало больше. Утверждать, что пропусков или
переделок стало статистически меньше, пока нельзя. Следующая сопоставимая задача
должна учитывать пропуски до/после реализации и время подготовки; автоматически
начинать её этим поручением не требуется.
