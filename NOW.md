## Что дал Горизонт 1

Пять действий, у каждого одна реализация с четырьмя лицами:

```
korkem_manufacturing/services/   правило           production, shop_floor, purchasing, dispatch, warehouse, scope, identity
korkem_manufacturing/api/        права + scope + аудит
korkem_ai/tools/                 ToolSpec.handler → та же функция API
mobile/korkem_flow/…/data/       POST на тот же эндпоинт
```

**«AI и кнопка вызывают одну функцию» — это тест, а не обещание:**
`assertIs(spec.handler, api.<action>)` для каждого из пяти.

**Разделение прав проявилось само**, когда действия стали публичными
эндпоинтами, и совпало с моделью ERPNext (проверено запросом к `DocPerm`):

```
Manufacturing User   запуск производства, закрытие стадии
Stock User           приёмка, отгрузка
Purchase User        заказ поставщику
```

**Домен не импортирует AI нигде** — проверяется `grep`, не обещанием.

**Каждый сервис, который пишет дважды, владеет savepoint.** Этот дефект нашли
дважды в разных местах: внешняя HTTP-транзакция не спасает, потому что
`registry.execute` возвращает исключение данными.

## Риски, которые надо держать на виду

**Bootstrap на чистом volume не проверен после миграции.** `bench get-app
--soft-link` требовал git-репозитория в приложении; после перехода на монорепо
`bootstrap.sh` делает три шага вручную (симлинк, `sites/apps.txt`,
`pip install -e`). Механизм сверен с рабочим стендом, `pip install -e` на
не-git директории проверен и вернул 0 — но полный bring-up с нуля никто не
запускал. **Самая рискованная операция репозитория.**

**Вендоры восстанавливаются, а не хранятся.** `scripts/fetch_vendor.sh`
по `vendor.lock`. До первого использования на чистой машине это тоже непроверено.

## Чего не трогать

- **Вендорные `erpnext/`, `frappe/`, `crm/`, `relaticle/`** — отдельные
  репозитории, должны оставаться чистыми. После любой пересборки:
  `git -C <repo> status` и откатить лишнее.
- **История прежних вложенных репозиториев** — бандлы в
  `~/korkem-git-backup-2026-08-31/`, проверены клонированием (51 и 18 коммитов).
  Не удалять, пока монорепо не отработает хотя бы один цикл.
- **Регрессионный тест на `signIn` без `AsyncValue.loading()`** — держит
  реальный баг, из-за которого ошибка входа выглядела как пустая форма.
- **`usage.record_turn` вместо `record` в обоих путях хода.** Упрощение обратно
  ломает четырнадцать канальных тестов; причина в докстринге.
- **Глобальный teardown каналов** — удаляет `Notification Delivery` и
  `Channel Event` целиком. Любую проверку снимать **до** следующего прогона.
