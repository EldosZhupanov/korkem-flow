# KORKEM Flow: Анализ текущего состояния архитектуры (Current State)

**Дата:** 2026-09-16  
**Роль:** Principal Software Architect, Staff Engineer, Product Systems Designer  
**Проект:** KORKEM Flow — локальная вертикальная операционная система (CRM + ERP + AI) для мебельных производств (2–15 сотрудников).

---

## 1. Обзор архитектуры и технологического стека

### 1.1 Архитектурная парадигма: Local-First Node (On-Premises Monolith)
В соответствии с `PLAN.md` (v2.0) и серией ADR (включая ADR-0016, ADR-0018, ADR-0024, ADR-0025, ADR-0026), KORKEM Flow спроектирован как **автономный узел предприятия (KORKEM Node)**.
- **Главный принцип:** Производственные данные (заказы, клиенты, чертежи, финансы, зарплаты, остатки) физически хранятся на оборудовании заказчика (мини-ПК, цеховой сервер или WSL2 на Windows-хосте). Облако KORKEM Cloud выполняет исключительно функции валидации лицензий, маршрутизации Web Push, сопряжения устройств и ретрансляции трафика без персистентного хранения бизнес-данных (R6).
- **Пять равноправных клиентов одного ядра (R3):**
  1. Desktop UI (Windows / Linux) — клиент локального узла на Flutter.
  2. Mobile UI (Android / подготовка iOS) — клиент на Flutter с автономной очередью исходящих мутаций.
  3. Терминал цеха (Shop Floor Tablet / PIN) — специализированный интерфейс рабочих сменных заданий.
  4. Каналы мессенджеров (Telegram / WhatsApp) — асинхронные боты-шлюзы для клиентов и мастеров.
  5. AI Ассистент — автономный агент, являющийся **клиентом** Service API, а не владельцем базы данных (R1, R2, R10).

### 1.2 Компоненты системы
1. **Backend (`backend/`):**
   - `korkem_manufacturing` — канонический доменный слой мебельного производства: доменные сервисы (`services/`), API-эндпоинты (`api/`), специфические DocTypes (`Capture`, `Furniture Material`, `Furniture Template`, `Furniture Hardware`, `Idempotency Record`), интеграции (БАЗИС XML, TrustMe, Kaspi).
   - `korkem_ai` — слой искусственного интеллекта: цикл рассуждения агента (`agent/loop.py`), реестр инструментов (`tools/registry.py`), роутер моделей (`orchestrator/router.py`), шлюз мессенджеров (`channels/gateway.py`), память фактов (`memory.py`), подтверждение опасных операций (`doctype/pending_action`).
   - `frappe` (v17 / develop, vendored) — системный веб-фреймворк: метаданные DocType, ORM, аутентификация, сессии, контроль доступа (RBAC), миграции, очереди задач (`frappe.enqueue`).
   - `erpnext` (vendored) — базовая учетная система: склад (Stock), закупки (Buying), производство (Manufacturing: Work Order, Job Card, BOM, Workstation), бухгалтерия (Accounts).
   - `crm` (vendored) — CRM на базе Frappe UI: лиды, сделки, контакты.
2. **Frontend (`mobile/korkem_flow/`):**
   - Flutter 3.44.8 / Dart 3.12.2.
   - Clean Architecture с Riverpod 3 (state management без кодогенерации).
   - Строгая дизайн-система токенов (`lib/core/design/tokens/` и `widgets/`).
   - Outbox мутаций (`lib/core/api/mutation_outbox.dart`) для работы при нестабильной связи.
   - Многоязычность (`ru`, `kk`, `en`).
3. **Инфраструктура (`infra/frappe_bench/`):**
   - Docker Compose: контейнеры `bench` (Frappe worker + web), `mariadb` (MariaDB 11.8), `redis-cache`, `redis-queue`.
   - Caddy в качестве reverse proxy с автоматическим управлением TLS и защитой заголовков.

## 2. Сильные стороны текущей системы

1. **Четкие фундаментальные инварианты (R1–R10):**
   Архитектура явно декларирует запрет на бизнес-логику внутри LLM (R1), обязательное прохождение всех операций через доменные сервисы (R2), изоляцию компаний (R4), недопустимость повышения роли (R5) и обязательное подтверждение человеком всех мутаций, инициированных AI (R10).
2. **Качественная реализация мобильного клиента:**
   - Строгий анализ (`flutter analyze` — 0 issues, `very_good_analysis`, strict-casts).
   - Чистая дизайн-система (токены цветов, отступов, радиусов, типографики; запрет жестко заданных литералов в виджетах).
   - Реализован паттерн `MutationOutbox` с клиентской генерацией `idempotency_key`, персистентным хранилищем неподтвержденных операций и корректной дедупликацией при ретраях.
3. **Глубокая мебельная специфика в домене:**
   - Парсер БАЗИС XML (`services/bazis.py`) с раскладкой панелей, кромки, фурнитуры и автоматической генерацией спецификаций (BOM).
   - Чистый модуль геометрических и материальных расчетов (`services/calculations.py`) на `Decimal`: расчет площадей фасадов, длины кромки, расхода плит с учетом запаса.
   - Проработанная цепочка от обращения (`Capture`) до гарантийного обслуживания (`Warranty`).
4. **Защита от MariaDB Deadlocks и идемпотентность:**
   `services/idempotency.py` использует сэйвпоинты транзакций, ловит `DuplicateEntryError` и `QueryDeadlockError (1020)`, предотвращая дублирование списаний и заказов при сетевых ретраях.
5. **Тестовая дисциплина:**
   В `korkem_manufacturing` реализовано более 420 интеграционных тестов; тесты проверяют реальные цепочки без моков LLM (`test_without_llm.py`).

## 3. Выявленный технический долг и слабые места

### 3.1 Архитектурный долг и отсутствие канонической State Machine
- **Размытый жизненный цикл заказа (Order Lifecycle):**
  Статусы заказа и производственных этапов не сведены в единый конечный автомат (State Machine).
  Состояние заказа фрагментировано между полями `status` и `docstatus` в ERPNext `Sales Order`, связанными документами `Contract`, `Capture`, `Task` (замер, дизайн, монтаж), `Delivery Note` и `Work Order`.
  Каждый сервис (`contract.py`, `design.py`, `dispatch.py`, `acceptance.py`) выполняет свои локальные ad-hoc проверки (`docstatus == 1`, `status not in UNSHIPPABLE` и т.д.). Отсутствует централизованный валидатор переходов (`can_transition(from_state, to_state)`), матрица разрешений по ролям и фиксация причин отказа.
- **Опасность race conditions и неконсистентных состояний:**
  Если при переводе заказа на следующий этап одна из операций падает после фиксации промежуточного документа, заказ остается в подвешенном состоянии без возможности автоматического отката (saga / compensation).

### 3.2 Надежность событий и отсутствие Transactional Outbox (P0 Reliability Gap)
- В `korkem_manufacturing/domain_events.py` реализован синхронный вызов подписчиков:
  ```python
  frappe.get_attr(dotted)(**payload)
  ```
- **Критический дефект:** Если доменный сервис изменяет данные в БД (например, создает заказ), а затем вызывает `domain_events.emit()`, подписчики (отправка сообщения в Telegram, пуш в телефон) выполняются **до коммита транзакции БД**.
  Если последующий код транзакции выбрасывает исключение, транзакция MariaDB откатывается (`rollback`), но внешнее действие (сообщение клиенту в Telegram: «Ваш заказ принят в производство!») уже необратимо ушло!
  И наоборот: если после коммита транзакции упал процесс или сеть, событие теряется навсегда.
  **Решение:** Необходим паттерн **Transactional Outbox**, сохраняющий события в отдельную таблицу `tabOutbox Event` в рамках той же транзакции БД с последующей гарантированной асинхронной доставкой воркером (At-Least-Once Delivery).

### 3.3 Аудит и трассировка (P0 Compliance & Traceability Gap)
- Отсутствует сквозной неизменяемый журнал бизнес-аудита (`AuditEvent` / `DomainActivityLog`).
- Документы Frappe сохраняют стандартные поля `modified_by` и `creation`, но не фиксируют:
  - точный контекст вызова (IP, канал: Web, Mobile, Telegram, AI Tool);
  - correlation ID цепочки операций;
  - дифференциальный снимок полей (diff до и после мутации);
  - бизнес-причину изменения статуса или списания материалов.

### 3.4 Изоляция арендаторов и безопасность (Tenant Isolation)
- Хотя по ADR-0018 KORKEM развертывается как single-tenant узел на фабрику, модуль памяти AI (`Memory Fact`) и CRM-сущности (`Customer`, `Lead`) имели уязвимости совместного доступа при наличии нескольких юридических лиц или филиалов (multi-company).
- В `korkem_ai/memory.py` только недавно был закрыт дефект утечки фактов между компаниями, однако системный механизм RLS (Row-Level Security) на уровне запросов к Frappe требует гарантированной фильтрации `company` во всех доменных выборках (`services/scope.py`).

### 3.5 AI Tools и безопасность (AI Architecture Gaps)
- В `korkem_ai/tools/` сохраняются устаревшие инструменты (`orders.py`, `production.py`, `buying.py`), напрямую манипулирующие DocTypes Frappe минуя доменные сервисы `korkem_manufacturing`.
- Отсутствует централизованный реестр инструментов с декларативным описанием уровней риска (Read-only, Reversible Mutation, Critical Financial/Production Mutation) и поддержкой двухуровневого подтверждения (Human-in-the-Loop).
- Нет полноценной телеметрии вызовов AI в стиле Langfuse: связки `trace_id` -> `run_id` -> `tool_call_id` с фиксацией входных токенов, латентности и стоимости по датированным тарифам.

### 3.6 Отсутствие пользовательского механизма автоматизации (Automation Engine)
- Владелец цеха не может настроить простейшие правила («Если замер выполнен -> назначить задачу дизайнеру», «Если остаток ЛДСП Дуб Сонома меньше 5 листов -> создать заявку на закупку») без написания Python-кода в `hooks.py`.
- Требуется декларативный движок автоматизации `Trigger -> Condition -> Action`, вдохновленный n8n, но строго ограниченный предметной областью мебельного цеха.

## 5. Вывод этапа 0
KORKEM обладает зрелым фундаментом и верными архитектурными принципами (PLAN.md R1–R10). Система НЕ требует разрушительного переписывания (big-bang rewrite).
Главная задача архитектурной модернизации:
1. Зацементировать ядро надежности: **Transactional Outbox**, **Order State Machine**, **Audit Trail**, **Strict Tenant Boundaries**.
2. Очистить границу AI: гарантировать, что ни один AI tool не трогает БД в обход доменных сервисов.
3. Обогатить доменную модель концепциями лучших мировых систем (ERPNext, Twenty, Temporal, n8n, Supabase, Langfuse), сохранив лаконичность вертикального решения для мебельного цеха.
