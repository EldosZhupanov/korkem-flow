### A. Какую проблему решает
Trigger.dev — современный фреймворк для отказоустойчивых фоновых задач (Durable Background Jobs) без ограничений по таймаутам (Serverless timeouts). Он решает проблему выполнения длительных, составных и ненадежных операций (обработка документов, генерация PDF, вызовы внешних LLM, отправка пачек уведомлений) с гарантией сохранения состояния каждого промежуточного шага, автоматическими повторами и дедупликацией.

---

### B. Архитектура системы
- **Архитектура v3 (Durable Execution Platform):**
  - `packages/core`: протоколы выполнения задач, контекст выполнения (`TaskRunContext`), стратегии повторов (`RetryOptions`), контрольные точки шагов.
  - `packages/trigger-sdk`: разработческий SDK для объявления задач: `task({ id: "my-task", run: async (payload, { ctx, step }) => ... })`.
  - `apps/webapp`: контрольная панель управления очередями, просмотра шагов, перезапуска упавших задач.
  - `packages/redis-worker`: распределенный исполнитель очередей с мониторингом heartbeat и обработкой аварийных остановок воркеров.
- **Принцип Step Run (Контрольные точки):**
  Внутри задачи каждый вызов оборачивается в `step.run("step-name", async () => ...)`. Результат шага сохраняется в персистентную БД.
  Если воркер аварийно падает на шаге 3, после перезапуска он НЕ выполняет заново шаги 1 и 2, а мгновенно восстанавливает их результаты из БД и продолжает с шага 3.

---

### C. Ключевые модули и файлы
- `packages/core/src/v3/taskRunContext.ts` — контекст выполнения с фиксацией `runId`, `attempt`, `idempotencyKey`.
- `packages/core/src/v3/retry.ts` — алгоритм экспоненциального бэкапа с джиттером (exponential backoff with jitter).
- `packages/core/src/v3/step.ts` — примитив контрольной точки с кешированием результата.
- `packages/redis-worker/src/` — надежная диспетчеризация очередей.

---

### D. Важные доменные абстракции
1. **Durable Task:** Фоновая задача с уникальным ключом идемпотентности, гарантирующая завершение даже при перезапуске контейнера или падении сети.
2. **Step Checkpoint:** Изолированная часть задачи, результат которой атомарно фиксируется в БД.
3. **Dead-Letter Handling:** Если задача превысила максимальное число повторов (например, 5 попыток с backoff), она переходит в статус `FAILED / DEAD_LETTER` с сохранением полного стектрейса и оповещением администратора.
4. **Idempotency Key Window:** Окно защиты от повторных запусков (например, повторный клик в приложении «Создать раскрой» в течение 1 часа переиспользует тот же `run_id`).

---

### E. Что уже есть в KORKEM
- В Frappe есть базовая очередь `frappe.enqueue`, использующая Redis RQ.
- В `korkem_manufacturing/services/idempotency.py` есть защита от повторных HTTP-запросов (`Idempotency Record`).
- В `korkem_ai/doctype/notification_delivery/` есть учет попыток доставки уведомлений (`retry_count`, `max_retries`).

---

### F. Чего не хватает в KORKEM по сравнению с Trigger.dev
- **Контрольных точек для тяжелых фоновых процессов:**
  В KORKEM есть критически важные фоновые операции:
  1. Импорт и разбор большого БАЗИС XML файла с созданием 50 панелей, 20 операций и спецификаций;
  2. Массовая отправка смет и договоров клиентам через WhatsApp;
  3. Пакетная обработка фотографий с замера (сжатие, удаление EXIF, анализ розетки/углов);
  4. Анализ чертежей мультимодальной LLM.
  Если сегодня при разборе XML на 40-й панели процесс падает (OOM или таймаут Frappe), транзакция откатывается целиком, и пользователю приходится загружать файл заново.
- **Отсутствия панели управления сбойными фоновыми задачами:** Директор или разработчик не видит в UI KORKEM списка задач в очереди, времени их исполнения и причин сбоев.

---

### G. Что KORKEM должен перенять концептуально
1. **Паттерн Durable Background Steps для тяжелых мебельных процессов:**
   Для импорта БАЗИС XML, генерации смет и AI-обработки фото внедрить пошаговое выполнение:
   - Шаг 1: Валидация файла и извлечение сырых деталей (Saved);
   - Шаг 2: Создание/поиск номенклатуры материалов (Saved);
   - Шаг 3: Формирование спецификации BOM (Saved);
   - Шаг 4: Генерация сменных заданий (Saved).
2. **Единый статус фонового задания (`DurableJobRun`):**
   `PENDING -> RUNNING -> COMPLETED / RETRYING / DEAD_LETTER`.

---

### H. Что KORKEM сознательно НЕ должен перенимать
- **Разворачивание облачного сервера Trigger.dev:**
  Trigger.dev требует отдельного кластера PostgreSQL, Redis и Next.js сервера. KORKEM — это локальный узел на MariaDB и Redis.
  Мы перенимаем **архитектурный паттерн Step Checkpoint & Retry**, реализуя его легковесно средствами Frappe/Python без добавления тяжелых внешних сервисов.

---

### I. Оценка трудоемкости внедрения
- Реализация механизма `durable_job` с сохранением промежуточных состояний шагов в MariaDB: **2 дня**.

---

### J. Архитектурные риски
- Увеличение объема записей в БД при подробном логировании каждого шага.
  *Решение:* Автоматическая очистка успешных шагов через 14 дней (TTL cleanup).

---

### K. Лицензионные последствия
- **Apache 2.0.** Лицензия пермиссивная. Паттерны шагов и бэкапа полностью безопасны для использования.
