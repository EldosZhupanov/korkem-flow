### A. Какую проблему решает
Medusa (v2) — модульная коммерческая платформа с гибкой оркестрацией бизнес-процессов (Composable Architecture). Решает задачу построения сложных распределенных сценариев оформления заказов, платежей, складских списаний и доставок через паттерн Workflow с обязательными компенсационными шагами (Saga Compensation Pattern).

---

### B. Архитектура системы
- **Модульная изоляция (`packages/modules/`):**
  Каждый домен (Order, Product, Stock Location, Inventory, Payment, Customer, Cart) оформлен в виде независимого модуля со своими сущностями и сервисами.
  Модули не вызывают друг друга напрямую через общие транзакции БД.
- **Движок рабочих процессов Medusa Workflows (`packages/core/workflows-sdk`):**
  Оркестрация строится из шагов (`createStep`):
  ```typescript
  const createOrderWorkflow = createWorkflow("create-order", function (input) {
    const reservation = reserveInventoryStep(input.items);
    const payment = processPaymentStep(input.payment);
    const order = createOrderStep(input);
    return order;
  });
  ```
  Для каждого шага обязательно определяется компенсаторная функция `compensate`, которая автоматически вызывается в обратном порядке при сбое последующего шага:
  - Если платеж упал -> вызвать компенсацию `releaseInventoryStep` (снять резерв со склада).

---

### C. Ключевые модули и файлы
- `packages/core/workflows-sdk/` — ядро декларативного описания графа шагов и компенсаций.
- `packages/modules/inventory/` — учет физических остатков и уровней резерва.
- `packages/modules/order/` — жизненный цикл заказа, редактирование состава после подтверждения (Order Edits / Changes).

---

### D. Важные доменные абстракции
1. **Workflow Step with Compensation:** Атомарное действие с гарантированным откатом при общем сбое цепочки.
2. **Order Edit / Change Request:** В производстве мебели клиент часто звонит через 3 дня после замера и говорит: «А давайте заменим ручки на профиль Gola и добавим ящик». В Medusa изменение заказа оформляется как черновик изменения (`OrderEdit`), пересчитывающий стоимость и разницу аванса, не ломая исходный заказ до утверждения.
3. **Payment Collection & Allocation:** Разделение понятий «Обязательство по оплате» и «Фактический платеж» (аванс 50%, доплата после отгрузки 40%, окончательный расчет 10% после подписания акта монтажа).

---

### E. Что уже есть в KORKEM
- В KORKEM есть разбиение на этапы предоплаты и окончательного расчета (`NOW.md`, `contract.py`, `invoicing.py`).
- Есть интеграция с Kaspi для приема платежей.

---

### F. Чего не хватает в KORKEM по сравнению с Medusa
- **Компенсаций при ошибках составных транзакций:**
  Если при переводе заказа в статус `IN_PRODUCTION` Work Order создался успешно, а списание плит упало из-за дефицита, система оставляет созданный пустой Work Order. Необходим атомарный откат (компенсация).
- **Механизма внесения изменений в утвержденный заказ (Change Orders):** Если клиент меняет цвет фасада после запуска, нет формализованной процедуры рекламации/изменения состава заказа с пересчетом себестоимости.

---

### G. Что KORKEM должен перенять концептуально
1. **Паттерн явных компенсационных шагов в доменных сервисах:**
   Оборачивать цепочки «Заказ -> Резерв -> Запуск» в управляемые блоки с откатом ранее выполненных шагов при исключении.
2. **Модель этапов оплаты (Deposit, Milestone, Acceptance Payment):**
   Привязать триггеры производства к долям оплаты:
   - Аванс >= 50% -> Разрешен запуск раскроя;
   - Доплата до 90% -> Разрешена отгрузка со склада;
   - Окончательный расчет 10% -> Заказ завершен, открыта гарантия.

---

### H. Что KORKEM сознательно НЕ должен перенимать
- **E-commerce специфику (Корзины, промокоды, дропшиппинг):** KORKEM — это позаказное производство мебели по индивидуальным проектам (BTO/ETO — Build-to-Order / Engineer-to-Order), а не интернет-магазин футболок.
