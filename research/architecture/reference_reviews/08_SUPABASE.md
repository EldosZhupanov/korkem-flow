# Reference Review 08: Supabase Backend Platform

**Репозиторий:** `supabase/supabase`  
**Лицензия:** Apache 2.0 / MIT / PostgreSQL License  
**Основной стек:** PostgreSQL, Elixir (Realtime), Go (GoTrue/Auth), TypeScript / Node.js  
**Приоритет анализа:** P0  

---

### A. Какую проблему решает
Supabase — open-source альтернатива Firebase на базе PostgreSQL. Предоставляет надежную платформу для веб- и мобильных приложений: реляционная СУБД с полной поддержкой SQL, декларативная изоляция арендаторов через Row-Level Security (RLS), встроенная аутентификация (GoTrue), подписка на изменения данных в реальном времени (Realtime) и объектное файловое хранилище (Storage).

---

### B. Архитектура системы
- **Postgres в центре архитектуры (Postgres-Centric Architecture):**
  В отличие от платформ, создающих свой закрытый ORM, Supabase делает СУБД первоклассным гражданином:
  - **Row-Level Security (RLS):** Безопасность гарантируется на уровне ядра СУБД, а не на уровне прикладного сервера. Даже при наличии уязвимости в контроллере злоумышленник не может прочитать чужую строку, если RLS-политика возвращает `FALSE`.
  - **Realtime Server (Elixir):** Подключается к слоту логической репликации Postgres (WAL) и транслирует изменения строк (INSERT, UPDATE, DELETE) по WebSockets клиентам с учетом прав доступа.
  - **Storage:** Хранилище файлов с метаданными в таблицах Postgres и авторизацией скачивания через RLS-политики.
  - **Auth (GoTrue):** Управление токенами JWT, сессиями и OAuth-провайдерами.

---

### C. Ключевые модули и архитектурные решения
- `docker/volumes/db/` — эталонные схемы инициализации, роли безопасности `anon`, `authenticated`, `service_role`.
- `apps/studio/` — интуитивный веб-интерфейс для работы с таблицами, индексами и политиками безопасности.
- Архитектурный шаблон изоляции тенантов:
  ```sql
  ALTER TABLE tabSalesOrder ENABLE ROW LEVEL SECURITY;
  CREATE POLICY company_isolation_policy ON tabSalesOrder
    FOR ALL
    USING (company_id = current_setting('app.current_company_id', true));
  ```

---

### D. Важные доменные абстракции
1. **Tenant RLS Policy:** Строгая гарантия невозможности утечки данных между организациями или филиалами на уровне базы данных.
2. **Realtime Broadcast & Presence:** Мгновенное оповещение экранов (например: мастер нажал «Распил завершен» на форматно-раскроечном станке — у диспетчера на Desktop статус заказа мгновенно сменился на «Кромление» без перезагрузки экрана).
3. **Signed Storage URLs:** Безопасный доступ к приватным файлам (фотографии замеров чужих квартир, сканы подписанных договоров с паспортными данными) через временные подписанные ссылки с ограниченным временем жизни (TTL).

---

### E. Что уже есть в KORKEM
- В KORKEM безопасность компаний реализована на уровне Python-сервисов (`korkem_manufacturing/services/scope.py: scoped()` и `ensure_company()`).
- В Frappe есть модуль `frappe/realtime/` на Socket.io и Redis Pub/Sub, умеющий отправлять события на клиенты.
- В Flutter-клиенте реализована подписка на сокет-события.

---

### F. Чего не хватает в KORKEM по сравнению с Supabase
- **Гарантии изоляции на уровне БД:**
  Поскольку KORKEM использует MariaDB и ORM Frappe, изоляция строится на дисциплине разработчика (не забыть обернуть фильтры в `scoped()`).
  В истории проекта уже были баги, когда запрос читал записи без проверки компании (`ai_agent_gap_analysis.md`, `NOW.md`).
- **Безопасных приватных ссылок на фотографии замера:**
  Фото замера (квартира клиента, планировка, розетки) загружаются во Frappe File. Если файл открытый, его URL статичен и доступен любому, кто знает имя файла. Необходимо генерировать временные токены доступа.

---

### G. Что KORKEM должен перенять концептуально
1. **Строгий Guard на уровне доменного репозитория (Fail-Closed Company Check):**
   Если в контексте запроса не установлена валидная компания (`company_id is None`), любой доменный сервис обязан выбрасывать исключение `SecurityException("Missing company scope")`, а не молча делать выборку по всей базе.
2. **Подписанные ссылки на чувствительные файлы:**
   Внедрить в `services/capture.py` и `services/measurement.py` генерацию защищенных одноразовых ссылок для просмотра фото замеров и чертежей.

---

### H. Что KORKEM сознательно НЕ должен перенимать
- **Миграцию с MariaDB/Frappe на Supabase Cloud:**
  KORKEM — это локальный монолитный узел (R6: данные у клиента). Тащить внешний Supabase или заменять весь стек MariaDB/Frappe на Postgres в рамках текущего продукта экономически нецелесообразно и сломает всю экосистему ERPNext.

---

### I. Оценка трудоемкости внедрения
- Внедрение fail-closed проверки скоупа компании в базовый `scope.py`: **0.5 дня**.
- Приватное хранение фото замеров: **1 день**.

---

### J. Архитектурные риски
- Риск блокировки системных фоновых воркеров при слишком жесткой проверке `company_id`.
  *Решение:* Предусмотреть явный доверенный контекст `system_context()` только для служебных миграций и cron-задач очистки.

---

### K. Лицензионные последствия
- **Apache 2.0.** Архитектурные паттерны RLS и хранения файлов безопасны.

---

### L. Итоговая рекомендация архитектора
**Одобрено (P0):**
Внедрить Supabase-подобный принцип **Fail-Closed Tenant Isolation** во все методы `korkem_manufacturing` и защитить доступ к фотографиям замеров и чертежам.
