# PLAN.md — целевая архитектура KORKEM Flow

**Версия:** 2.0 · **Дата:** 2026-08-31
**Статус:** активный. Заменяет `docs/archive/research/master_execution_prompt.md`.

Этот документ отвечает на вопрос **«что мы строим и по каким законам»**.
Что строим прямо сейчас — `NOW.md`. В каком порядке — `ROADMAP.md`.
Чем продукт является и не является — `PROJECT.md`.

---

## 1. Что это за продукт

KORKEM Flow — **локальная операционная система мебельного предприятия**.

Не Flutter-приложение к ERPNext. Не облачный SaaS. Предприятие покупает
систему, ставит её у себя, и его производственные данные никогда не покидают
его здание.

Пять равноправных входов в одно ядро:

```
   Desktop UI        Mobile        Терминал цеха      Telegram/WhatsApp        AI
   Windows/Linux    Android        PIN, планшет         бот-канал         ассистент
        │              │                │                    │                │
        └──────────────┴────────────────┴────────────────────┴────────────────┘
                                        │
                            ┌───────────▼────────────┐
                            │   KORKEM Service API   │   ← сюда идёт КАЖДАЯ запись
                            └───────────┬────────────┘
                                        │
                            ┌───────────▼────────────┐
                            │   KORKEM Domain        │   korkem_manufacturing
                            │   бизнес-правила       │
                            └───────────┬────────────┘
                                        │
                            ┌───────────▼────────────┐
                            │  ERPNext · Frappe · CRM│
                            └───────────┬────────────┘
                                        │
                            ┌───────────▼────────────┐
                            │  Диск клиента          │   БД, файлы, бэкапы
                            └────────────────────────┘
```

**AI — один из клиентов API, а не хозяин ERP.** Это главное отличие от того,
что построено сегодня, и причина, по которой Горизонт 1 идёт до всего
остального.

## 2. Десять инвариантов

Нарушение любого — дефект проектирования, а не вопрос вкуса. Полный текст с
пояснениями — в скилле `.claude/skills/korkem-architecture/SKILL.md`, который
агент обязан прочитать перед проектированием.

| | Правило |
|---|---|
| **R1** | AI не содержит бизнес-логики |
| **R2** | Любая запись проходит через доменный сервис |
| **R3** | Desktop, Mobile, терминал, мессенджеры и AI используют один Service API |
| **R4** | Каждый запрос несёт scope компании, определённый сервером |
| **R5** | Пользователь не может повысить себе роль |
| **R6** | Производственные данные хранятся у клиента |
| **R7** | Система работает без LLM |
| **R8** | Система честно деградирует без интернета |
| **R9** | Любое опасное действие: проверка прав + запись в аудит |
| **R10** | Любая запись от AI подтверждается человеком |

## 3. Узел (Node) — где на самом деле живёт система

### 3.1 Узел — служба, а не окно

`KORKEM Node` — это Frappe + ERPNext + `korkem_manufacturing` + `korkem_ai` +
MariaDB + Redis + воркеры + файловое хранилище. Он запускается как **системная
служба** и продолжает работать, когда директор закрыл ноутбук.

Desktop UI — **клиент своего же узла**, ровно как телефон. Это снимает
проблему «выключил ноутбук — цех встал»: она возникает только если UI и узел
это один процесс.

### 3.2 Жёсткое ограничение: Frappe не работает на Windows нативно

**Это надо решить до того, как обещать `KORKEM Flow Desktop.exe`.** Frappe
требует Linux. В этом репозитории стенд существует **только** как Docker
Compose; нативной установки под Windows нет и у апстрима она не
поддерживается. Варианты:

| вариант | цена |
|---|---|
| Docker Desktop как зависимость | платная подписка для бизнеса от 250 сотрудников / $10M выручки |
| WSL2 + образ дистрибутива | нужна виртуализация в BIOS; память WSL — отдельная настройка, которая уже кусалась на этой машине |
| маленькая Linux-ВМ в поставке | большой инсталлятор, свои проблемы с сетью и дисками |
| **отдельная Linux-коробка** | mini-PC или NAS — **рекомендуется** |

**Решение:** узел — это Linux-приложение. Основной сценарий — mini-PC или NAS
в цехе. `.exe` под Windows — это **клиент и установщик-менеджер узла**, а не
сам узел. Для мастерской из двух человек допустим fallback: узел в WSL2 на той
же машине, но это поддерживаемый запасной путь, а не главная история.

### 3.3 Форма поставки — решено: WSL2 на машине, которая уже стоит

**`ADR-0024`.** Раздел раньше описывал mini-PC как отправную точку. Владелец
продукта решил иначе, и по хорошей причине: пилот, который начинается с
закупки железа, не начинается. Узел ставится на компьютер, который у клиента
уже есть, в WSL2 — Frappe нативно под Windows не работает (§3.2), а Linux-слой
там уже штатный.

Это решение про **срок входа, а не про качество площадки**, и стоит оно
конкретных работ, а не оговорок: автозагрузка (WSL сам не стартует), проброс
портов, переживающий смену NAT-адреса при каждой перезагрузке, и выкладка
бэкапа **наружу** из виртуального диска. Всё перечислено в `ADR-0024` и
`docs/operations/WINDOWS_NODE.md`.

**Mini-PC остаётся правильным вторым шагом**, когда пилот подтвердится:
переезд — это перенос того же compose-стека, и он дешевле, чем ожидание
закупки сейчас.

В любом варианте данные у клиента. Разница — в железе, не в архитектуре.

### 3.4 Раскладка хранилища

```
/korkem/            (или D:\KORKEM\ на Windows-хосте через WSL)
├── database/       MariaDB
├── files/          drawings · measurements · contracts · photos · approvals
├── backups/
├── ai/             knowledge · embeddings
├── logs/
└── config/
```

Путь выбирается при установке и меняется из админ-панели. Смена пути — это
операция «остановить узел → перенести → переписать конфиг → проверить
восстановление», а не изменение одной строки; она должна быть реализована как
процедура с проверкой, а не как поле ввода.

### 3.5 Как телефон находит узел

Это самая недооценённая часть. Frappe резолвит сайт **по заголовку `Host`**,
поэтому имя сайта надо решить при установке и оно должно работать со всех
сторон.

| откуда | как |
|---|---|
| Desktop на том же хосте | `127.0.0.1` |
| телефон в LAN | адрес Windows-хоста + проброс портов; **не** адрес WSL — он меняется при каждой перезагрузке (`ADR-0024`) |
| телефон вне LAN | ретранслятор KORKEM Cloud (только транспорт, без хранения) — спроектирован в `ADR-0026`, границы в `ADR-0025` |
| эмулятор Android | `10.0.2.2` |

Привязка устройства — **код сопряжения**, показанный на Desktop и введённый на
телефоне; после сопряжения телефон хранит адрес узла и токен. Никакого ввода
IP руками работником цеха.

## 4. Личность и организация

### 4.1 Противоречие, которое надо снять

«Данные у клиента» и «вход через Google» противоречат друг другу: OAuth требует
интернета и внешнего провайдера. Решение — **двухуровневая личность**:

- **Узел владеет пользователями.** Frappe `User` — источник правды.
- **OAuth — только удобный вход**, который отображается на локального
  пользователя. У каждого пользователя дополнительно есть локальный
  аутентификатор (пароль или PIN), работающий при выключенном интернете.
- **KORKEM Cloud хранит только связку** `organization_id ↔ oauth_subject` и
  маршрут push-уведомлений. Ни одной бизнес-записи.

**Никогда не делать внешнего провайдера единственным входом в собственную
систему фабрики.**

### 4.2 Провайдеры входа, по приоритету

`Email/пароль` и `PIN` — обязательны и работают офлайн.
`Google`, `Apple`, `Microsoft`, `Телефон` — удобство.
`Discord` — **не делать.** Это не деловой провайдер личности.

### 4.3 Первый пользователь и приглашения

Установивший систему создаёт организацию и становится `OWNER` — единственная
роль, возникающая сама. Все остальные **приглашаются**: администратор заводит
сотрудника с должностью и подразделением, человек принимает приглашение.

Работник никогда не создаёт себе предприятие.

### 4.4 Шаблоны ролей

Роли — это **Frappe Roles + фикстуры прав**, версионируемые в
`korkem_manufacturing`, а не настройки, накликанные в Desk. Иначе второй
клиент получит другую систему безопасности.

```
OWNER · DIRECTOR · ADMINISTRATOR · ACCOUNTANT
SALES_MANAGER · DESIGNER · MEASURER
PRODUCTION_MANAGER · WAREHOUSE · QUALITY_CONTROL
CUTTING_OPERATOR · EDGEBANDING_OPERATOR · CNC_OPERATOR
PAINTER · ASSEMBLER · INSTALLER · DRIVER
```

Каждая роль — это **и права, и стартовый экран**. Фрезеровщик не видит CRM,
маржу, счета, закупочные цены и чужие зарплаты — не потому что кнопка скрыта,
а потому что сервер откажет (R5, R9).

## 5. Офлайн — три разные задачи, которые обычно путают

**Узел офлайн — тривиально.** Он локальный: производство, склад, задачи,
терминалы, отчёты работают всегда. Отваливается только внешнее — OAuth,
Telegram, WhatsApp, облачные LLM. Каждое обязано сказать, что именно
отвалилось, а не крутить спиннер.

**Телефон вне LAN — это задача синхронизации, и её надо решать дёшево.**
Рекомендация: **не строить двунаправленную синхронизацию.** Вместо этого —
**исходящая очередь** на клиенте: действие ставится в очередь с
идемпотентным ключом, воспроизводится при возврате связи, сервер отбрасывает
дубликат. Примитив уже есть — `Pending Action` и `turn_id`; его надо
расширить, а не изобретать CRDT. Полноценная синхронизация — это месяцы и она
не нужна ни одному из сценариев.

**Локальная LLM — режим деградации.** Ollama-провайдер уже реализован. Без
интернета ассистент отвечает хуже, но продукт работает — по R7 он и так обязан
работать без модели вовсе.

## 6. Одна задача, много каналов

Назначение работы — **один `Task` в ERP**. Telegram, WhatsApp и push —
**каналы доставки**, а не три отдельные задачи.

```
assign_work()  →  Task
                   ├── push
                   ├── Telegram   [Принять] [Не могу] [Открыть]
                   └── WhatsApp
```

Нажатие «Принять» в Telegram делает ровно то же, что кнопка в приложении:
вызывает тот же сервис, ставит `status`, `employee`, `accepted_at`, `source`.

**Это дёшево, потому что механика уже есть:** `Notification Delivery` с
повторами, `Channel Event`, `turn_id`, протокол подтверждающих кнопок и
классификация отказов провайдера — всё построено и протестировано в фазах
27–33. Не строить заново, подключить к сервису.

## 7. Что хранит облако KORKEM

Хранит: лицензию, манифест обновлений, `organization_id`, публичные ключи,
маршрутизацию push, bootstrap OAuth, опционально — зашифрованный блоб бэкапа,
**который KORKEM не может прочитать** (ключ у клиента).

Не хранит: заказы, клиентов, зарплаты, BOM, финансы, фотографии, чертежи,
сотрудников — ничего производственного.

**Лицензия проверяется офлайн.** Подписанный файл с сроком и льготным
периодом, проверяемый узлом по публичному ключу. Схема «не дозвонился —
не работаешь» для завода неприемлема.

---

## 8. Две вещи, которые локальность делает обязательными

**Бэкап — это функция продукта, а не хорошая практика.** Если у клиента умрёт
SSD, продукт убил его бизнес. Значит: автоматический бэкап на второй диск,
**проверенное восстановление** (бэкап, который ни разу не разворачивали, — это
вера), и опциональный зашифрованный офсайт.

**Обновление происходит N раз, иногда офлайн.** Миграции обязаны быть
идемпотентными, а узел обязан **отказаться стартовать** на данных новее своего
кода, а не мигрировать наполовину. Механизм есть — патчи Frappe.

| сегодня | цель |

## 10. Что сознательно **не** делаем

- **Не строим двунаправленную синхронизацию.** Очередь исходящих + идемпотентность.
- **Не строим свой планировщик, свой склад, свою себестоимость.** Всё это есть в ERPNext.
- **Не строим микросервисы.** ADR-0016: агенты — один процесс.
- **Не строим мультиарендность сейчас.** ADR-0018. Один узел — одна компания, зафиксировано письменно.
- **Не тащим Firebase.** Он переносит владение данными и личностью в Google — прямое нарушение R6.
- **Не делаем Discord входом.**
- **Не делаем iOS до пилота.** Нужен Mac, платный аккаунт и ревью; цех — на Android.
- **Не делаем двенадцать агентов из PROJECT.md.** Реальная архитектура — один цикл с вызовом инструментов, и он работает лучше. Либо строить осознанно, либо закрыть план.

## 11. Честная оценка объёма

Одиннадцать горизонтов из `ROADMAP.md` — это **12–18 месяцев для одного
инженера** в темпе, который виден в истории коммитов. Это не повод сокращать
список, это повод не обещать сроки, которых не будет.

Порядок в роадмапе выбран так, чтобы **каждый горизонт что-то давал в
эксплуатацию**, а не только приближал финал. Если ресурс кончится на Горизонте
4, у клиента останется работающая система — узкая, но настоящая.
