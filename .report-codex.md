# Отчёт Codex — изоляция новой цепочки между компаниями

Дата: 2026-09-03. Проверена цепочка
`Capture → Customer → Opportunity → CRM Task` для двух настоящих Company и
двух пользователей, связанных с ними через ERPNext `User Permission`.

## Вердикт по четырём звеньям

| звено | до проверки | итог |
|---|---|---|
| `Capture` | не течёт | list, named GET и `api.capture.stats` изолированы Company User Permission |
| `Opportunity` | не течёт | list и named GET скрывают Opportunity компании B от A |
| `CRM Task` на `Capture` | **тёк** | исправлено; list и named GET, включая настоящий HTTP, теперь закрыты |
| `Customer` | виден обеим компаниям | это осознанный shared master текущей модели, зафиксирован тестом |

Customer в ERPNext не имеет `company`. Поэтому пользователь A видит Customer,
созданного при конвертации Capture B, и `customer_candidates` возвращает его
вместе с `mobile_no`. Сейчас это не считается дефектом: клиент общий для узла.
Если владелец решит, что клиент принадлежит одной компании, потребуется решение
о модели данных; случайно вывести это из существующей схемы нельзя. Решение
зафиксировано постоянным regression test и docstring службы `enquiry`.

## Найденные утечки

До исправления целевой модуль дал фактический результат:

```text
Ran 10 tests in 20.865s
FAILED (failures=4)
```

Полный лог: `korkem-clean-bench-1:/tmp/run-014908.log`.

1. CRM Task, ссылающийся на чужой Capture, возвращался в collection GET и
   named GET. Настоящий `/api/resource/CRM Task/<name>` отвечал HTTP 200.
2. `POST api.capture.record` принимал `assign_to` сотрудника компании B от
   пользователя A, создавал Task с текстом Capture и отвечал HTTP 200.
3. `POST api.enquiry.convert` так же принимал иностранного `assign_measurer`,
   конвертировал Capture A и отвечал HTTP 200.

Четвёртый failure в логе — HTTP-проверка того же CRM Task, а не отдельный
четвёртый root cause.

## Исправления

### Scope CRM Task

У CRM Task нет собственного `company`, но у задачи новой цепочки компания
однозначна: `reference_doctype = Capture`, а Capture содержит Company.

Добавлен узкий `services/task_scope.py`:

- `permission_query_conditions` наследует Company от Capture для list;
- `has_permission` применяет то же правило к named GET и операциям с документом;
- задачи Work Order, CRM Deal и остальных reference types не переопределены.

Это намеренно не маскирует известную отдельную проблему общих CRM Task на
`CRM Deal`: у Deal/Lead нет согласованной модели Company, и эта продуктовая
развилка остаётся прежней.

### Scope исполнителя

В существующий `services.scope` добавлена одна серверная проверка
`ensure_user_in_company`: assignee обязан иметь Company User Permission той же
компании. Она вызывается до любых записей:

- в `capture.record` — до создания Capture;
- в `enquiry.convert` — до Customer и Opportunity.

Поэтому отказ не оставляет частичный Capture, Customer, Opportunity или Task.
`Administrator` оставлен платформенным исключением для существующих Desk и
операционных сценариев; реальные сотрудники onboarding всегда имеют явную
Company binding.

## Endpoint-проверка

Тесты не ограничиваются прямым вызовом Python. Использован Frappe WSGI test
client и реальный SID пользователя компании A.

Проверено:

- `/api/resource/Capture/<foreign>` — отказ;
- `/api/resource/Opportunity/<foreign>` — отказ;
- `/api/resource/CRM Task/<foreign>` — отказ после исправления;
- `GET korkem_manufacturing.api.capture.stats` считает только Company A;
- `POST korkem_manufacturing.api.enquiry.convert` не принимает foreign Capture;
- оба POST не принимают сотрудника B как assignee для данных A;
- `GET customer_candidates` показывает Customer B — намеренно, по shared-master модели.

Traceback `PermissionError` в полном зелёном выводе печатает сам WSGI client для
ожидаемых HTTP 403; итог unittest при этом `OK`.

## Соседняя функциональная находка

Тестовый пользователь только с `Sales Manager` не смог создать Customer.
ERPNext manager-role не включает права `Sales User`; после добавления обеих
штатных ролей fixture смог выполнить положительную цепочку.

Сейчас invitation mapping должности `manager` выдаёт только `Sales Manager`.
Если приглашённый менеджер должен сам конвертировать Capture, это отдельный
функциональный gap. В этой security-задаче role semantics не менялась.
